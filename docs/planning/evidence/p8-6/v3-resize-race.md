## 2. 十次失敗在失敗當下讀到的狀態

每一次都失敗在同一行：測試最後把視窗由 1024×768 改回 1440×1000、重新打開清單，`reframed()` 通過之後的 `expectLabelsClear()`。下表是那一次 `page.evaluate` 實際回傳的值（由 trace 取出）。

| # | 距離 `setViewportSize(1440×1000)` | 讀到的 canvas | 失敗的斷言 |
|---|---|---|---|
| 1 | 273 ms | 1024×768 | 雲端基礎設施島的名牌在地圖外（x = −76.6） |
| 2 | 323 ms | 1440×768 | Kubernetes 島的名牌在清單下 |
| 3 | 305 ms | 1024×768 | 雲端基礎設施島的名牌在地圖外 |
| 4 | 250 ms | 1024×768 | 同上 |
| 5 | 269 ms | 1024×768 | 同上 |
| 6 | 239 ms | 1440×768 | Kubernetes 島的名牌在清單下 |
| 7 | 258 ms | 1440×768 | 同上 |
| 8 | 153 ms | 1024×768 | 雲端基礎設施島的名牌在地圖外 |
| 9 | 72 ms | 1024×768 | 同上 |
| 10 | 294 ms | 1024×768 | 同上 |

- 十次裡 canvas **沒有一次**是 1440×1000：七次還是上一個視窗的尺寸，三次只有寬度到位。
- 七次「在地圖外」的那一刻，名牌已經是大名牌（寬 145–216 px；`matchMedia` 立即生效），位置卻還是 1024 px 取景算出來的，清單在 x = 1100–1440——所以「沒有名牌在清單下」成立。
- **十次失敗裡，`reframed()` 都是第一次輪詢就回傳 0**（trace 中每次只有一筆、回傳值 0）：它一次也沒有等。三次「在清單下」是它通過之後、檢查之前，寬度剛好到位而相機還沒重新取景。
- 失敗截圖（失敗後才拍）是正確的畫面：六個名牌都在地圖內、不在清單下。產品最後會到位。

## 3. 成功與失敗的差別

| | 成功 | 失敗 |
|---|---|---|
| `reframed()` 通過時的 canvas | 1440×1000（R3F 已處理 resize） | 1024×768 或 1440×768 |
| 名牌位置 | 新取景 | 舊取景 |
| 相機 | 已依新尺寸與清單寬度重新取景並畫出 | 還沒有 |

## 4. 根因

測試同步競態，不是產品缺陷。`reframed()` 等的條件是「沒有名牌壓在清單下」，但這個條件在**視窗已改、場景還沒跟上**的過渡狀態下也成立，所以它沒有等到重新取景；接著的檢查讀到的是舊尺寸的版面。機器越忙，瀏覽器處理 resize（ResizeObserver → R3F 設定 canvas 尺寸 → 相機取景 → 下一幀畫出）的時間越長，撞上的機率越高。

不是 `requestAnimationFrame` 沒有觸發，也不是相機沒有要求重繪（P8.3 已補 `invalidate()`）：每一次失敗的截圖都顯示場景之後正確到位。

## 5. 修正（只改測試的等待條件）

`reframed()` 改為等「真的重新取景完成」：

1. 視窗是測試設定的尺寸（`innerWidth`／`innerHeight`）。
2. canvas 的尺寸等於它的舞台（R3F 已處理 resize）。
3. canvas 與每個名牌的位置，連續兩個 animation frame 沒有變動。
4. 沒有名牌在清單下（原本的條件）。

沒有固定等待、沒有改任何斷言、沒有 skip、沒有 retries；`expectLabelsClear()` 的三條規則原封不動。產品程式沒有修改。
