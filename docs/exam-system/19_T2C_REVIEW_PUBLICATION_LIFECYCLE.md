# 19 審核與發布生命週期（T.2C）

- **範圍**：Shared Trial System 的題目審核、核准與發布流程，供 iPAS 模擬考與日後其他認證題庫共用。
- **本階段沒有**：核准任何題目、發布任何 iPAS 題目、建立網頁上的審核或發布介面。審核帳本目前是空的。
- **程式**：`src/lib/trials/lifecycle.ts`（純函式）、`src/lib/trials/import.ts`（匯入只反映狀態）、`scripts/trials/review.ts`、`scripts/trials/publish.ts`、`scripts/trials/ledger-io.ts`、`scripts/trials/review-packet.ts`。
- **資料**：`src/content/trials/ledger.json`（審核帳本）、`docs/exam-system/data/ipas-review-queue.json`（iPAS 審核準備資料，不是審核紀錄）。

## 1. 狀態轉換

| 狀態 | 進入條件 | 誰能讓它發生 | 網站可見 |
|---|---|---|---|
| `in-review` | 匯入的題目；或目前版本沒有有效的人工核准；或最新決定是「要求修改／退回」 | 匯入流程（預設） | 否 |
| `approved` | 審核帳本中，**目前版本＋內容雜湊**的最新人工決定是核准，且確認了必要項目（AI 撰寫：`answer-verified`；官方題：`source-checked`） | `review.ts apply --confirm N`，由帳本授權的審核者 | 否 |
| `published` | 已核准的同一版本＋雜湊，另外經過發布動作，帳本有發布紀錄 | `publish.ts --confirm N`，由帳本授權的發布者 | 是（`isPlayable`） |

- **三者不得混用**：AI 自動品質檢查（docs 15–18 的 AI QA Passed）不會寫入帳本，也不構成核准；人工核准不會讓題目發布；發布只能透過發布關卡。
- **綁定版本**：每筆審核與發布紀錄都記下題目 ID、版本與內容雜湊（`revisionHash`：題幹、選項、答案、配分）。題目修改後產生新版本與新雜湊，舊的核准與發布不會延續，題目自動回到 `in-review`。
- **過期與竄改**：審核決定若不是目前版本或雜湊不符，整批拒絕（stale）。帳本中雜湊與內容不符、由未授權者做出、或沒有核准支撐的發布紀錄，都由 `checkLedger` 回報；匯入與重建時視為錯誤。
- **可追溯**：帳本只增不刪。「要求修改」與「退回」必須寫明原因（`note`），之後的核准不會覆蓋歷史，只取同一版本的最新決定。
- **匯入不發布**：匯入流程不會新增審核紀錄，也不會提升狀態。批次檔中的 `reviews` 只是 T.2C 以前的註記，不構成核准；其中要求修改或退回的註記仍會讓題目暫緩。
- **發布後修改**：已發布的版本雜湊記在 `published-hashes.json`，不得改變（匯入時檢查）；修改必須新增版本，新版本要重新審核與發布。

## 2. 相容性：T.2C 以前發布的 53 題

- 53 題（MVP 原創 13 題、114 年普考計算機概要 40 題）在 T.2C 以前由匯入流程發布，`published-hashes.json` 記有它們的 57 個版本雜湊。
- 它們的目前版本雜湊已記錄，所以維持 `published`，不需要帳本紀錄；產生的檔案逐位元組不變，57 個雜湊不變。
- 測試凍結這條路徑：`published-hashes.json` 中的每個鍵，不是這 53 題，就必須有帳本的發布紀錄（`tests/trials-lifecycle.test.ts`）。
- 這 53 題日後若新增版本，新版本同樣要經過審核與發布關卡。

## 3. 批次審核流程（本機 CLI）

```
node --experimental-transform-types --no-warnings --import ./scripts/trials/register.mjs scripts/trials/review.ts status
node … scripts/trials/review.ts packet ipas-aiap-basic-d --out <本機資料夾> --from 1 --count 25
node … scripts/trials/review.ts apply <檔案>.decisions.json                 # 試算：逐筆檢查，不寫入
node … scripts/trials/review.ts apply <檔案>.decisions.json --confirm 25    # 全部寫入或全部不寫
```

- **審核包**：每次 10–25 題（批次最後一包可少於 10 題）。逐題顯示題幹、選項、答案、解析、考綱、子主題、題型與難度、時效、AI 自動檢查結果、相似性風險、標記、避免同卷的題目、待人工確認事項與必須確認的項目；第一優先的題目標為「⚠ 高風險」。產生審核包只讀取資料，不改變任何狀態。
- **審核包含未發布題目的答案與解析**：`--out` 必須指定網站與版本控制以外的資料夾。
- **決定檔**：審核包同時產生 `.decisions.json`，每題已填入目前的版本與雜湊，`verdict` 留空；沒有填寫的決定檔無法套用，避免誤核准。批次操作就是在同一個檔案中填寫多筆決定。
- **確認步驟**：`--confirm N` 的 N 必須等於決定筆數。任何一筆無效（過期、雜湊不符、缺少確認項目、退回沒有原因、超過 25 筆、審核者未授權）就整批不寫入。
- **寫入**：帳本與重建後的題目檔一起寫入，全部成功或全部不變（`writeAllOrNothing`）。寫入前先確認每個批次的產生檔與批次檔同步，不同步就拒絕。

## 4. 發布關卡

```
node … scripts/trials/publish.ts ipas-aiap-basic-d-91@1 --by owner --at 2026-12-01               # 試算
node … scripts/trials/publish.ts ipas-aiap-basic-d-91@1 --by owner --at 2026-12-01 --confirm 1   # 發布
```

- 只發布指名的版本，而且必須是目前版本；重新計算內容雜湊，必須等於人工核准時的雜湊；該版本最新的人工決定必須是核准並確認必要項目；`--by` 必須有發布權限；`--confirm` 必須等於版本數。任何一項不符就整批不發布。
- 發布會寫入帳本的發布紀錄、重建題目檔（狀態變為 `published`，題目記錄 `review.publication`），並在 `published-hashes.json` 加入該版本雜湊。
- 匯入、批次審核與一般建置都不會發布：狀態只能由帳本中的發布紀錄產生，而發布紀錄只由 `publish.ts` 寫入。
- 本階段只以測試與隔離副本驗證發布能力，沒有發布任何 iPAS 題目。

## 5. 曝光控制

| 資料流 | 現況與控制 | 證據 |
|---|---|---|
| 伺服器端題庫載入 | `trialBank` 含全部題目（含審稿中），只在建置時於伺服器端使用；頁面查題只透過 `playableById`（只含已發布題目） | `tests/trials-exposure.test.ts` |
| 頁面與元件 | 審核包、帳本、匯入流程、生命週期模組與 scripts 都不被 `src/app`、`src/components` 引用 | 同上（靜態掃描） |
| 靜態頁面 | 試煉頁面全部預先產生，`dynamicParams = false`；未開啟功能旗標時全部 404 | 同上；建置輸出 |
| 公開試煉路由 | 只有已有試卷的考試會產生路由；iPAS 沒有試卷，`/trials/ipas-aiap-basic` 為 404 | 執行期探測 |
| 錯題本（`/trials/review`） | 只傳已發布題目（`playableQuestions`） | 測試與執行期探測 |
| API／Server Actions／Middleware | 不存在；網站沒有任何寫入途徑 | 測試（檔案掃描） |
| 用戶端 bundle 與預先產生的頁面 | 不含任何 iPAS 題目 ID 或題文 | 建置後掃描 `.next/static` 與 `.next/server/app` 的 html／rsc |
| 伺服器 bundle | 含整個題庫模組（建置時使用）；沒有任何對外路徑會回傳它 | 建置後掃描與執行期探測 |

- **已知限制（不是未發布題目的曝光）**：網站沒有後端，作答在瀏覽器內計分，所以**已發布**試卷的正解與解析會隨頁面資料送到瀏覽器。這是 T.0 的設計；若模擬考需要防止作答前取得答案，需要伺服器端計分，屬於後續工作。
- **審核介面**：目前沒有身分驗證與授權機制，所以**不建立網頁審核或發布介面**；審核與發布只在本機以 CLI 執行。

## 6. 尚未啟用的安全功能

1. **身分驗證**：帳本的審核者名單（`reviewers`）是授權清單，不是身分驗證；任何能修改 repository 的人都能編輯帳本。目前靠版本控制的審查、`checkLedger` 與測試把關。若要多人審核，需要真正的身分驗證，並考慮簽章或由受保護的流程寫入帳本。
2. **網頁審核介面**：在身分驗證完成前不建立。
3. **伺服器端計分**：見 §5 的已知限制。
4. **下架與退役**：發布後撤回（`retired`）的流程尚未納入發布關卡；目前只能新增版本或依既有的 `retired` 欄位處理。
5. **CI 強制**：雜湊凍結與帳本檢查目前由測試執行；尚未設定在合併前強制執行的 CI。

## 7. iPAS 審核準備

- **資料**：`docs/exam-system/data/ipas-review-queue.json`，整合 docs 15–18：每題的 AI 自動檢查結果（全部 AI QA Passed）、相似性風險、標記（法規、易變、相似性中、匯入前重新設計、考點重疊）、待人工確認事項、避免同卷的題目。
- **文件層級核准**：Q01–Q20 的 20 筆文件層級人工核准保留為參考（版本、答案、日期），**沒有寫入帳本**，題目仍是 `in-review`；審核包會顯示它們，並在版本不同時提示必須重新審核。
- **第一優先（12 題）**：
  - 法規與時效：Q05、Q19（批次 A）、Q94、Q96（批次 D）；
  - 相似性風險中：Q45、Q47（批次 B）、Q56、Q69（批次 C）、Q77、Q78、Q89、Q93（批次 D）。
- **第二優先**：匯入前重新設計過的題目（docs 16–18）。其餘依批次順序審核。
- **進度**：`review.ts status`。目前 100 題全部 `in-review`，帳本 0 筆審核、0 筆發布。

## 8. iPAS 模擬考整合的下一步

1. 依第一優先順序產生審核包，人工審核並以 `review.ts apply` 記錄決定；需要修訂的題目改批次檔、新增版本後重新審核。
2. 兩科各 50 題都核准後，再以 `publish.ts` 發布（可分批）。
3. 發布後建立兩份固定試卷（每科 50 題 × 2 分、75 分鐘、70 分及格），避開 docs 15–18 列出的同卷組合；試卷只能引用已發布的版本。
4. 建置前檢查 2027-05 的 `reviewBy` 複查日（Q05、Q19、Q94、Q96）。
5. 評估是否需要伺服器端計分（§5），以及多人審核時的身分驗證（§6）。
