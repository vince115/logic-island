# 教材撰寫指南（Content Authoring Guide）

> Phase E.1，E.2、E.3、E.4 更新（2026-10-31）。把一堂「規劃中」的課完成為「完整教材」的步驟與標準。欄位規則見 [LESSON_CONTENT_SCHEMA](LESSON_CONTENT_SCHEMA.md)，課程順序見 [PHASE_E_CURRICULUM](PHASE_E_CURRICULUM.md)。範例：`src/content/curriculum/content/F01.ts`～`F05.ts`。

## 1. 流程

1. 確認這堂課在 `lessons.ts` 的大綱（目標、概念、先修、視覺化類型）仍然合理；要調整就一起改，並重新產生課綱規格的課程表。
2. 若課程的視覺化類型還是 planned：先實作它（`src/components/curriculum/visualizations.tsx` 與 schema 的設定型別），在 `registry.ts` 改為 implemented。不要用靜態圖片或假的按鈕代替。
3. 新增 `content/<lessonId>.ts`，匯出 `LessonContent`，在 `index.ts` 的 `contents` 加入。
4. 在 `lessons.ts` 把這堂課改為 `status: 'complete'`、`version: '1.0.0'`。
5. 執行 `tests/curriculum.test.ts`（規則）與 `tests/curriculum-code.test.ts`（每段程式實際執行），全部通過，而且 Java 不能是略過狀態：把 JDK 放在 PATH 上再跑，例如本機 IntelliJ IDEA 附帶的 JDK：`PATH="/Applications/IntelliJ IDEA.app/Contents/jbr/Contents/Home/bin:$PATH"`。Java 以 `javac --release 17` 編譯，確保不會用到 Java 17 之後的 API。輸出比對只去掉結尾空白，開頭的空白（例如金字塔圖形）也會被檢查。
6. 在瀏覽器檢查桌機與手機版面（`/curriculum/<slug>`），並更新課綱規格 §5。

## 2. 內容標準

- **用繁體中文寫給第一次學的人**：先說為什麼需要，再說怎麼做，最後說常見錯誤。專業術語第一次出現時附英文（例如「指定（assignment）」）。
- **每段都要有教學價值**：避免「本節介紹…」「非常重要」這類空話；用具體例子、數字與反例說明。
- **先寫「為什麼要學」**：`motivation` 用一兩句說明這個主題能解決什麼問題，不寫空泛的「很重要」。
- **把常見錯誤寫出來**：每堂至少一個 `warning` callout，說明初學者實際會犯的錯（例如 F04 的 C++ 連續比較、F05 的 `=` 與 `==`）。
- **三語差異是內容**：語言行為不同時（整數除法、型別、讀取方式）要明確比較，不要只寫其中一種。
- **只寫已確認的事實**：語言行為以實際執行或語言規格為準；涉及 APCS 時只寫能力類型，不寫題號、級分或保證。

## 3. 程式碼

- 三語都要寫，而且**用各語言自然的寫法**，不逐行翻譯：C++ 用 `std::` 與 `"\n"`（不使用 `using namespace std` 與 `endl`），Python 用 `map(int, input().split())`、f-string、`divmod` 等慣用法，Java 一律 `public class Main`、用 `Scanner` 或 `String.format`。
- C++ 以 C++17 編譯，需通過 `-Wall -Werror`；Python 3；Java 17 以上。
- 每堂至少 3 個範例，各自示範不同的重點（例如：基本用法、常見模式、陷阱或語言差異）。
- 程式要短：範例以 5～25 行為原則，只示範本課的觀念。
- 三種語言的結果真的不同時（陣列複製、區塊作用域、負數除法），不要硬改成一樣：寫 `outputByLanguage`，並在正文解釋差異。
- 在 TypeScript 中用 ``String.raw`…` ``（檔案中的 `const code = String.raw`）撰寫程式碼，`"\n"` 才會保持原樣；不要在程式碼中使用 `${`。
- 每個範例都寫 `output`（以及讀輸入時的 `stdin`）；三語輸出不同時（例如負數除法）寫 `outputByLanguage`，並在正文說明原因。
- 輸出盡量使用 ASCII 文字，避免各平台編碼差異；浮點數一律指定小數位數。

## 4. 觀念測驗

- 至少 4 題，每題考一個本課的觀念；題型要混合程式碼閱讀、執行結果推理與錯誤辨識，不要全是記憶題，最好是學生真的會答錯的地方（程式追蹤、邊界、語言差異）。
- 選項要像真的答案；錯誤選項來自常見誤解，而不是明顯荒謬的句子。
- 解析要說明「為什麼對」以及「錯的選項錯在哪」，必要時給驗算過程。
- 有程式片段時放在 `code`，並註明語言。

## 5. 程式練習

- 題目要寫清楚：敘述、輸入格式、輸出格式、限制（範圍）、至少一組範例與說明。
- 測資至少包含：一般（normal）、邊界（edge：最小值、最大值、分界點、可能溢位的值）、以及錯誤輸入（error）——題目保證輸入合法時，改寫 `errorPolicy` 說明原因。
- 參考解答三語都要能通過全部測資（`tests/curriculum-code.test.ts` 會執行）。
- 在本課之前還沒教到的語法（例如 F01、F02 還沒教輸入）用 `starter` 提供，讓學習者只寫本課的部分。
- E.1 沒有線上評測：`judge` 一律是 `'none'`，頁面會說明「請在自己的電腦上執行並比對測資」。**不得**新增會在伺服器或瀏覽器執行使用者程式碼的功能（`eval`、未隔離的執行器、執行程式碼的 API），除非另有經過審查的安全設計並獲批准。

## 6. 視覺化（E.2 起共用元件）

- 只在能幫助理解時使用；設定放在內容檔，不寫在元件裡。
- 不要為一堂課寫新的 React 元件：迴圈、陣列、函式呼叫、遞迴都用共用 trace 的步驟資料描述（見 LESSON_CONTENT_SCHEMA §5.1），元件會依資料顯示對應的面板。
- 每一步的 `note` 要說明「這一行做了什麼、為什麼」，而不是重複程式碼；狀態以文字呈現（成立／不成立、讀取／寫入／越界、執行中／等待中）。
- 複雜度只能呈現為「公式計算的操作次數」的示意模型，不得呈現為實測時間。
- 某堂課不適合互動視覺化時，類型設為 `none` 並在正文用表格、圖示或逐步說明代替，不放假的互動元件。
- **資料結構（E.3）**：不要手寫結構的每一步，改用 `src/content/curriculum/simulate.ts` 的模擬器：在內容檔列出操作（每個操作附上它在 trace 程式中的行號），模擬器實際執行並產生步驟，例如 `steps: containerSteps('stack', 'stack', [{ line: 4, op: 'push', value: '(' }, …])`。模擬器的說明文字（擴容、碰撞、上浮下沉、路徑壓縮）已寫好；需要額外的 `vars` 或 `output` 時，對回傳的步驟做 `map`。結構與模擬器不符時（例如一般樹、完全二元樹的陣列表示）才手寫步驟，並保持面板資料一致（驗證器會檢查）。
- **演算法（E.4）**：搜尋、排序、雙指標、視窗、前綴和、遞迴樹、回溯、貪心、BFS、DFS、Dijkstra、DP 表格與背包都用 `src/content/curriculum/simulate-algorithms.ts`；每個模擬器接受 `lines`（事件名稱 → trace 程式的行號）。trace 程式必須和模擬器做「完全相同」的演算法（同樣的 pivot 規則、迴圈形狀、相等時的處理），步驟才不會和程式不一致。需要不同的變數名稱或更細的行號時，對回傳的步驟做 `map`。一般樹、格子模擬等模擬器沒有涵蓋的情形，在內容檔寫一個小函式實際執行同樣的規則來產生步驟，不要手打每一步。
- **用自己的輸入（tryIt）**：陣列演算法、BFS／DFS／Dijkstra 與背包可以加 `tryIt`；輸入的格式與範圍由元件檢查，教材只需提供初始資料。說明文字要寫出演算法的前提（已排序、非負、非負權重）。
- **自己試試**：堆疊、佇列、雙端佇列、動態陣列、鏈結串列、雜湊集合、BST、堆積、並查集可以加上 `playground`，讓學習者用自己的值操作；輸入範圍與元素上限由元件固定，教材不需要另外寫限制。
- **雜湊的示意函數**：視覺化用「整數 mod m」或「字元碼總和 mod m」說明桶的位置，正文要說明這是教學用的示意，實際語言的雜湊函數不同，而且 `unordered_map`／`HashMap`／`set` 的走訪順序不可依賴（範例輸出前先排序）。
- **容量成長**：動態陣列的視覺化採「容量加倍」模型；實際成長比例依實作而不同（libstdc++ 約 2 倍、Java `ArrayList` 約 1.5 倍、CPython 約 1.125 倍），範例不得輸出 `capacity()`。
- `ds-comparison`：每個操作寫成本（Big-O 文字，攤銷或平均要寫明）與是否適合；結論只能來自這些資料，不寫成「實測比較」。
- `variable-state`：程式選本課的核心片段（可與範例不同語言），每一步寫「這一行做了什麼」，`vars` 是執行完這一行之後的值，字串值加引號。
- `conditional-branch`：分支依程式中的順序排列，`result` 要和參考解答的輸出一致（`tests/curriculum.test.ts` 會比對 F05 的邊界值）。

## 7. 完成前檢查清單

- [ ] 至少 3 個學習目標，內容逐一涵蓋
- [ ] `motivation` 說明為什麼要學
- [ ] 至少 3 個段落，含常見錯誤的提醒
- [ ] 至少 3 個範例，三語齊全、輸出已驗證（C++、Python、Java 都已執行）
- [ ] 若課程加入 JavaScript（`extraLanguages: ['JavaScript']`）：每個範例、參考解答與 starter 都有 JavaScript，以 Node.js 執行（標準輸入用 `require("fs").readFileSync(0, "utf8")`），輸出與其他語言一致；正文列出語言語法的句子補上 JavaScript；`tests/curriculum-code.test.ts` 會自動執行
- [ ] 至少 4 題測驗（含程式閱讀與錯誤辨識），每題有解析，答案已再次核對
- [ ] 至少 1 題練習，含一般、邊界與錯誤（或 `errorPolicy`）測資，三語參考解答通過
- [ ] 視覺化已實作且設定正確（或課程不使用視覺化）
- [ ] 資料結構的步驟由模擬器產生（或手寫時面板資料一致）；範例不輸出雜湊容器的走訪順序或容量
- [ ] 練習的預期輸出由參考程式或暴力法實際執行產生（不手算）；測資能區分錯誤的做法（重複值、負數、空或單一元素、到不了的節點、溢位）；大型測資在頁面上只顯示開頭（自動測試仍使用完整內容），單一輸出遠小於 1 MB
- [ ] 每題測驗的答案都已執行或逐步追蹤確認；APCS 只寫能力對應，不寫官方題號、出處或級分
- [ ] `lessons.ts` 狀態為 complete、版本 1.0.0；課綱規格已更新
- [ ] 桌機與手機（360／390 px）沒有水平溢出、按鈕有名稱
