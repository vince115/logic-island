# D.3-6a Environment Architecture Refactor（純架構重構）（2026-10-31）

> 授權範圍：把 `hex-world-scene.tsx` 寫死的光源、背景與陰影設定抽成環境資料（`src/lib/islands/environments.ts`）與 `HexEnvironment`（`hex-world/hex-environment.tsx`），為 D.3-6b 的四種時間情境打底。**只有中午一種環境**，畫面維持不變。不做清晨／黃昏／傍晚、不加時間情境 UI、不加 PointLight／Bloom；不改 GLB、地形、教材、資產庫；不啟用候選頁的自由相機或 Auto Orbit；不切換正式 `/islands`；不 merge、不 push。基準：`57364a2`（D.3-5b）。

## 1. 結果摘要

- 環境改成一份可 JSON 序列化的資料：背景、環境光、半球光、太陽（顏色、強度、位置）、陰影（map 大小、bias、far）、霧（`null`＝不畫）、發光倍率 `glow`。目前只有 `ENVIRONMENTS.noon`，數值與 D.2c 接受的 `contrast` 光照逐項相同；A2 預覽頁（`/islands/hex`）原本較亮的補光保留為 `PREVIEW_NOON`（同一個中午，只是補光不同，不是時間情境）。
- `HexEnvironment` 集中畫背景、霧（有設定才畫）、三盞燈與太陽陰影，並帶著 D.2c-2 的 `StaticShadows`（原樣搬移）。場景只傳入環境與陰影範圍。
- `frameloop="demand"` 與靜態陰影的重畫機制不變；另外補上「太陽或陰影範圍改變時，重算陰影相機投影並重畫一次陰影」，中午不會觸發（§3.2）。
- GLB 的發光材質（`LLv2_Warm_Emission`）改成每次掛載自己的一份複本，只複製這個材質；色盤材質仍是快取裡共用的那一份。發光強度由環境的 `glow` 乘上模型自己的強度，中午 `glow` 為 1（§3.3）。
- 霧：定義了設定但不啟用（§3.4 的量測）。
- 與 `57364a2` 比較：六條 `/islands` 路由在桌機與手機模擬下 24 張畫面 0 像素差，頁面按鈕與連結、編譯的 WebGL program／shader、draw call、三角形、陰影 pass 都相同（§5、§6.1）。時間指標（SwiftShader 模擬）判定為 **Performance Inconclusive（輕微）**：鏡頭飛行與環繞 FPS 未觀察到可穩定重現的下降；首幀只有桌機 A2 預覽留下未確認的 +108 ms 訊號，原因不明，列為後續驗證（§6.6）。

## 3. 設計重點

### 3.1 環境資料

- 欄位：`background`、`ambient {color, intensity}`、`hemisphere {sky, ground, intensity}`、`sun {color, intensity, position}`、`shadow {mapSize, bias, normalBias, far}`、`fog {color, near, far} | null`、`glow`。顏色一律 `#rrggbb` 字串、位置是 `[x, y, z]` 陣列，`JSON.parse(JSON.stringify(env))` 與原物件相同（單元測試）。日後可直接從 JSON 讀入；本階段**不做** Phase E 的 schema、loader 或驗證器。
- 太陽位置以地圖中心為原點（場景原點本來就是地圖中心，地圖群組平移 `-ox, -oz`），照向中心；與原本 `[-12, 22, 10]` 相同。
- 陰影範圍（`shadowExtent`）由世界大小算出，不屬於環境，仍由場景傳入；左右 ±extent、上下 ±(extent − 2) 不變。
- 原本 `ambientLight`／`directionalLight` 沒有寫顏色（three 預設白色），資料裡明寫 `#ffffff`，值相同。
- 未放進資料：tone mapping 與曝光（Canvas 預設，沒有寫死在場景）、海面色調（D.3-6b 才需要）、`continuousOcean` 以外的備用海面平面色（屬於海面，不是環境）。

### 3.2 陰影重畫條件（為未來光源方向檢查）

- D.2c-2 的 `StaticShadows` 只看「可見投影物件的 id 與位置」，**光源方向不在判斷鍵裡**；另外 three 只在第一次建立陰影貼圖時計算陰影相機的投影（`WebGLShadowMap.js` 建立 map 時呼叫 `shadow.camera.updateProjectionMatrix()`），R3F 改 `shadow-camera-*` 屬性也不會重算。所以 D.3-6b 若只改太陽位置或陰影範圍，靜態陰影會停在舊的樣子。
- `HexEnvironment` 以「太陽位置｜陰影範圍｜far」為鍵：鍵改變時，在新燈光屬性觸發的那一幀、陰影 pass 之前，重算陰影相機投影並設 `gl.shadowMap.needsUpdate = true`。掛載時鍵不變，所以**中午完全不觸發**（掛載時不多 `invalidate`、不多畫一次陰影）。
- 動態陰影（19 格原型、A2 預覽用 `soft`）每幀都畫陰影，只需要重算投影，同一段程式也會做。
- 實驗驗證（只在 scratch 建置）見 §3.5。

### 3.3 GLB 發光材質

- v2.1 GLB 只有兩個材質：`LLv2_Palette_VertexColor`（所有建築、樹木）與 `LLv2_Warm_Emission`（`KHR_materials_emissive_strength` 強度 2；`Light_Lantern`、`Lighthouse_WindowGlow`、`Route_LampGlow`）。六角世界的三個頁面（A2、19 格、37 格；候選頁與 37 格同一份配置）只放燈塔、工坊、碼頭（A2 另有三棵 GLB 樹），所以場景裡用到發光材質的只有燈塔的兩個部件。
- 問題：`scene.clone(true)` 與 `node.clone(true)` 都共用材質，drei 的 `useGLTF` 依 URL 快取一份場景，GLB 樹木（`hex-nature.tsx`）直接用快取的色盤材質，舊版 `/islands` 的 `glb-island-model.tsx` 也用同一個快取。若 D.3-6b 直接改快取裡的 `emissiveIntensity`，會影響每個掛載與 `/islands/legacy`。
- 做法：`ownGlowMaterials()` 只把「`MeshStandardMaterial`、`emissiveIntensity > 0`、emissive 不是黑色（或有 emissive 貼圖）」的材質換成複本，同一次掛載裡共用一份；色盤材質不複製。`useGlow` 讓複本的強度＝模型自己的強度 × 環境 `glow`；只有不同時才改並要求一幀，中午（`glow` 1）什麼都不做。卸載時只釋放複本，不釋放快取。
- 複本與原材質參數完全相同，所以 three 的 program cache 用同一個 shader（§5：每條路由編譯的 program 與 shader 數量和 `57364a2` 相同），draw call 也相同（mesh 數不變）。
- 廣場燈籠是 `hex-plaza.tsx` 自己建立的材質，不共用，直接接上 `useGlow`。載入中／失敗時的暫代幾何（`HexLandmarks`）不跟著 `glow`，D.3-6b 若需要再處理。

### 3.4 霧（Fog）的評估：定義但不啟用

量測在 scratch 實驗建置（不在 repo）：同一份 D.3-6a 程式，另外允許「載入前指定環境」與「執行中直接改 `scene.fog`」。37 格實驗室頁、桌機、headless Chromium＋SwiftShader，**模擬數字，不是真機**。霧色＝背景色 `#cbe9f4`。

| 情境 | 首幀（3 輪） | 編譯的 program／shader | 鏡頭飛行 FPS | 與無霧的像素差 |
|---|---|---|---|---|
| 無霧（`fog: null`，現行） | 1,623／1,537／1,554 ms | 17／34 | 42.2 | — |
| 看不見的霧（near 1000、far 2000） | 1,639／1,605／1,636 ms | 17／34 | 42.4 | **0** |
| 看得見的霧（near 45、far 90） | 1,572／1,621／1,586 ms | 17／34 | 42.2 | 141,827（約 26%） |

| 執行中切換 | 結果 |
|---|---|
| 無霧時一般重畫（CPU 端，`gl.render`） | 0.3～0.5 ms |
| 加上霧後的第一次重畫 | **84.1 ms**：program 17→27、shader 34→54（畫面用到的 program 全部另編一份有霧的版本） |
| 再拿掉霧 | 0.7 ms（無霧版本仍在快取，program 維持 27） |

- 載入時就有霧：每個材質編譯的是「有霧版本」，數量不變；首幀與飛行 FPS 的差異在 SwiftShader 的雜訊內。但每個片段都多一段霧的計算（深度 smoothstep 與一次混色），即使看不見也一樣；這個成本在 SwiftShader 量不出來，真機也還沒量。
- 執行中從無到有：所有材質重新編譯，這一幀卡住（SwiftShader 84 ms；真機的編譯時間不同，但一樣會卡）。
- 結論：依授權條件「會造成額外 shader 成本就先定義不啟用」，D.3-6a 的中午 `fog: null`，`HexEnvironment` 支援有設定時畫霧，型別已定義。給 D.3-6b 的建議：**不要讓霧在情境之間有／無切換**；要嘛四個情境都沒有霧，要嘛四個都從載入就有霧、只改參數（中午用看不見的範圍）。另外正交相機的霧依「視線深度」計算，而 D.3-5a 的近平面保護會隨仰角把相機距離從 40 拉到最多約 61（手機），所以固定的 near／far 會讓霧隨傾斜改變，D.3-6b 需以相機距離換算或改用其他做法。

### 3.5 太陽／陰影範圍改變的實驗

同一份 scratch 建置，37 格實驗室頁，桌機。為排除 P1-29（§3.6）的干擾，量測前先讓頁面畫一幀「什麼都沒變」的畫面。

| 做法 | 之後畫的幀 | 其中重畫陰影 | 停止後 2 秒 | 與「直接以該設定載入」的像素差 |
|---|---|---|---|---|
| 經由環境資料改太陽位置（−20, 14, −6）與陰影 far（70→24），即 D.3-6b 的路徑 | 1 | **1** | 0 | **0** |
| 對照：繞過 `HexEnvironment` 直接移動燈光（只有 D.2c-2 的判斷鍵） | 1 | 0 | — | 36,134（陰影停在舊方向） |

- 重複 3 次結果相同。far 也改了而結果與重新載入相同，表示陰影相機投影確實重算。
- 說明：D.2c-2 的判斷鍵本身看不到燈光改變；`HexEnvironment` 的鍵讓「改一次環境＝只多畫一次陰影」，之後閒置 0。

### 3.6 驗證時發現的既有問題（P1-29，未修改）

實驗中發現，37 格實驗室頁載入穩定後的**第一次互動**常會多重畫一次陰影，之後不會；`57364a2` 與 D.3-6a 一樣（滾輪各三次：`57364a2` 1／0／0、D.3-6a 1／0／0）。原因是 `StaticShadows` 在 render 更新世界矩陣之前記錄投影物件位置，GLB 掛載那一幀記到的是尚未更新的矩陣。陰影結果正確，只是多一次 pass。本輪原樣搬移、不改；記為 KNOWN_ISSUES P1-29。D.3-6b 量「切換只重畫一次」時要先讓頁面畫過一幀。

### 3.7 P1-28 與相機

- 鏡頭飛行在閒置後第一幀跳一大段（P1-28）是 D.3-5b 已記錄的既有行為；本輪沒有修改 `hex-camera.tsx` 或時間步進，也不把它算成 D.3-6a 的回歸。§6 的飛行 FPS 兩個版本都受它影響。
- 新增的 `useFrame` 回呼（`HexEnvironment` 一個、`useGlow` 每個使用者一個）在 demand 模式下不會要求畫面，只在有畫面時各做一次比較；不改相機或名牌的更新順序。

### 6.6 結論：Performance Inconclusive（輕微）

- **確定相同**：draw call、三角形、陰影 pass、shader／program 數量、24 張畫面的像素、頁面按鈕與連結、停止後閒置重畫 0。
- **鏡頭飛行、環繞 FPS**：未觀察到可穩定重現的下降（平衡組與配對測試都在 ±2.5% 內、方向不一）。第 4 組的大幅下降在配對測試沒有重現。
- **首幀**：多數路由與裝置未觀察到可穩定重現的下降；**桌機 A2 預覽**在配對測試仍有 +108 ms（+9.2%）的未確認訊號，原因不明、未能歸因於 D.3-6a 的任何程式。因此效能判定為 **Inconclusive**，不是 Pass，也**不宣稱兩版效能相同或新程式沒有成本**；目前沒有明確重大退化的證據。
- 依「功能、視覺、draw call、shader 數量都符合基準，且沒有明確重大退化證據」的條件提交，並留下後續驗證：
  1. 候選頁整合（D.3-5c／D.3-6c）的 Level 3 驗收時，在較安靜的機器上以配對方式重量首幀，A2 預覽與候選頁各至少 12 對。
  2. D.3-4B 真機量測時一併記錄首幀；若真機也出現同方向差距，再做定向 profiling。
- 真機數字：Not Measured（D.3-4B）。

## 7. 未解決問題與給 D.3-6b 的事項

1. **效能 Inconclusive（輕微，KNOWN_ISSUES P1-30）**：桌機 A2 預覽首幀的未確認訊號，後續驗證見 §6.6。本輪所有效能數字都是 SwiftShader 模擬；真機 GPU、iOS Safari 仍待 D.3-4B。
2. **P1-28（既有，未修改）**：鏡頭飛行閒置後第一幀跳動；與 D.3-6a 無關，兩版都有。
3. **P1-29（既有，新記錄，未修改）**：載入後第一次互動常多畫一次靜態陰影（§3.6）。D.3-6b 驗收「切換只重畫一次陰影」前要先讓頁面畫過一幀。
4. **霧**：只定義不啟用。D.3-6b 需決定「四個情境都沒有霧」或「從載入就常駐、只改參數」，不要有／無切換（§3.4）；並處理相機距離隨仰角改變對視線深度霧的影響。
5. **低太陽的陰影範圍**：本輪只保證「改了會重算並重畫」。分析紀錄 §0.1 #6 的光源距離與 far 問題（仰角越低需要越遠、越深的陰影相機）仍屬 D.3-6b，需依太陽方向計算位置與 far。
6. **環境資料尚未涵蓋**：海面色調、名牌等 HTML 的配色、tone mapping／曝光；暫代幾何（載入中／失敗時）的發光不跟 `glow`。
7. **候選頁**：只因共用 `HexWorldScene` 而經過新程式，畫面、DOM、shader 與 draw call 都與 `57364a2` 相同；沒有啟用自由相機或 Auto Orbit。
8. **選擇環境的方式**：目前仍由既有的 `lighting` 選項決定（`contrast`＝中午、預設＝A2 預覽補光）。D.3-6b 加入其他時間時需要新的場景選項，本輪不加。
