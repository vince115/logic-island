## 5. 工具自我檢查的數字（不是真機結果）

### 5.1 Chromium（SwiftShader）

真機工具在 Chromium 跑 1 輪（self-test），與桌機 harness 同一台機器、同一份 build：

| | 工具：候選頁 | 工具：舊版 | harness：候選頁 | harness：舊版 |
|---|---|---|---|---|
| 桌機 飛行 FPS | 50.7 | 60 | 48.6、51.4 | 60 |
| 桌機 首幀 | 1,337 ms | 786 ms | 1,437～1,537 ms | 820 ms |
| 手機模擬 飛行 FPS | 59.8 | 60 | 59.8 | 60 |
| 手機模擬 首幀 | 1,443 ms | 799 ms | 1,457～1,471 ms | 820～823 ms |
| 全景／聚焦／陰影 draw call（桌機） | 43／26／0 | 146／82／112 | 43／26／0 | 146／82／112 |
| 聚焦 draw call（手機模擬） | 26 | 45 | 26 | 45 |

- 每幀成本兩邊逐項相同；FPS 與首幀在同一範圍（SwiftShader 下時間受機器負載影響，P1-20）。
- 工具判定三項都「不可靠」：軟體算圖、少於 3 輪（桌機另有「不是手機」），**符合設計**。
- harness 的 A/B：`72e3eb6` 的 `perf/world.perf.ts` 與目前版本交錯跑（各 2 次），draw call、三角形逐項相同，候選頁桌機 FPS 48、47.3 對 48.6、51.4，手機模擬都是 59.2～59.8。另有一次在剛跑完平行 E2E、load average 14～18 時量到候選頁 32.6／38.5 FPS，A/B 確認是機器負載而非搬移造成。

### 5.2 桌機 Safari dry-run（真 WebKit，Apple GPU；不是手機）

目的是確認注入的程式在 Safari（WebKit）上能跑：用 `open -a Safari` 開啟自動量測（Safari 27.0.1，DPR 1，畫布 885×600）。

| | 候選頁 | 舊版 |
|---|---|---|
| 有效頁數 | 1（另 1 頁量測中 Safari 被切到背景，記為失敗） | 2 |
| 首幀（熱快取） | 492 ms | 406、412 ms（中位數 412） |
| 首幀（冷快取，暖身） | 3,641 ms | 418 ms |
| GLB 就緒 | 530 ms | 520 ms |
| 鏡頭飛行 FPS | 60 | 60 |
| 幀間隔 p95 | 18 ms | 18 ms |
| 全景／聚焦／陰影 draw call | 43／26／0 | 146／78／112 |
| 閒置重畫 | 0 | 0 |
| 工具判定 | 三項都「不可靠」：不是手機、頁面曾在背景、少於 3 輪 | — |

- Safari 量到的每幀成本與 Chromium 完全相同（候選頁全景 43 個 draw call／28,569 個三角形、聚焦 26／38,339），表示注入程式在 WebKit 上正確計數，兩個瀏覽器畫的是同一個場景。
- 第 6 頁量測時 Safari 視窗被切到背景，rAF 停止、run 停住；工具把那頁記為「頁面被切到背景」並不判定，**符合設計**。之後未再把 Safari 拉到前景，run 以 6／8 頁取消。真機上同樣情況要重跑整個 run（驗收表 §2.2）。
- dry-run 也抓到一個工具 bug：背景頁面原本被算進中位數（FPS 變成 NaN 並誤判「不穩定」）；已修正為不計入中位數、旗標保留，並補單元測試。
- 冷快取首幀候選頁 3.6 秒、舊版 0.4 秒：冷快取那一次包含第一次下載 JavaScript 與 GLB，且候選頁是第一個載入的頁面；只有一筆樣本，不能當結論。真機會在暖身那次記錄（P-07），不列入門檻。
