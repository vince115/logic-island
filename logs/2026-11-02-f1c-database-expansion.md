## stdin 阻塞：根因與修正（Batch 1）

F.1b 的紀錄說原因是「沒有測資的範例繼承了 Vitest 的標準輸入」。這是錯的：原本的執行器一律以 `input` 傳入測資（沒有測資時是空字串）。

證據：讓父行程的 stdin 保持開啟，再以 `spawnSync` 分別傳空字串、傳資料、不傳 `input`；三種情況下子行程都立即收到 EOF。A06 的程式碼測試在背景、不重新導向的情況下也在 4 秒內跑完。

真正的原因（重現）：

- 測資是由 `spawnSync` 寫進管線的。多個測試並行時，讀取全部標準輸入的 JavaScript 程式（`readFileSync(0)`，129 個範例與解答都這樣讀）偶爾等不到輸入結束。
- 重現方式：A08 `e-count-at-most` 的 400 KB 測資，8 個並行 worker、共 4,000 次執行，其中 6 次卡住；正常一次約 30 ms。
- 執行又是同步呼叫、沒有逾時，Vitest 自己的測試逾時中斷不了它，所以整個測試一直等。
- 加上逾時的第一版執行器，在完整 Vitest 裡把這個卡住變成了可見的失敗：A08 `e-count-at-most` 超過 20 秒被終止。

修正（`tests/support/run-program.ts`，`curriculum-code.test.ts` 與 `examples.test.ts` 共用）：

- 測資寫入暫存檔，以檔案作為子行程的標準輸入；沒有測資時是 `/dev/null`。檔案一定會結束，不再經過管線。
- stdout 與 stderr 都擷取，不寫到測試程序自己的輸出。
- 每次執行都有逾時：程式 20 秒、編譯 90 秒；逾時以 SIGKILL 結束子行程，並回報清楚的錯誤。
- 暫存檔在每次執行後刪除。

驗證：

- 同樣的壓力測試 4,000 次，0 次卡住、0 次輸出錯誤；之後沒有殘留的暫存檔，也沒有孤兒行程。
- 新的回歸測試（`tests/run-program.test.ts`）涵蓋：
  - 沒有測資時立即收到 EOF；
  - 測資逐字送達，而且是檔案、不是管線；
  - 測試程序自己的 stdin 一直開著時，也不會交給子行程；
  - 逾時的程式被終止，行程已不存在；
  - 失敗的程式回報 exit code 與 stderr。
- 教材範例的預期輸出與覆蓋率不變。完整 Vitest 在背景、不加 `< /dev/null` 也能正常結束。

## 新活動（Batch 2a）

- query-plan（T2）：
  - SQL 練習場把 `EXPLAIN QUERY PLAN` 的結果寫成有名稱的步驟：全表掃描、掃描整個索引、索引搜尋、讀取中間結果、額外排序。每次執行都顯示 SQLite 的執行時間。
  - 練習以「計畫要求」判定（`src/lib/sql/plan.ts`），不比對計畫文字，因為學習者的索引名稱與表別名都不同：
    - `maxFullScans`：計算全表掃描與整個索引的掃描；讀取 CTE 或 `FROM` 子查詢的中間結果不算；LEFT JOIN 內表的整表掃描要算；
    - `noTempSort`：不需要額外排序；
    - `indexOn`：指定的表要經由索引讀取。
  - 要求可以放在檢查敘述上（例如建索引後的固定查詢），也可以放在查詢練習上（結果正確，而且計畫也要符合）。
  - B+ 樹探索（`src/lib/bplus/tree.ts`）：照順序插入（葉節點分裂時複製鍵上去、內部節點分裂時把鍵移上去）、點查詢的路徑、沿葉節點鏈的範圍查詢。學習者可以換自己的鍵與階數，輸入會先驗證；有重設。
- transaction-timeline（T1）：
  - 單一連線（`src/lib/txn/recovery.ts`）：write-ahead log 的教學模型（不是某個產品的檔案格式）。包含自動提交、CHECK 拒絕、SAVEPOINT／ROLLBACK TO／RELEASE；可以在任一步之後當機，復原只保留日誌裡有 COMMIT 紀錄的交易。測試確認任一步當機後的復原結果，都等於當時已提交的狀態。
  - 兩筆交易交錯（`src/lib/txn/schedule.ts`），兩個教學模型：
    - 鎖：嚴格兩階段鎖，四種等級，有等待，死結時中止提出請求的一方；
    - MVCC：PostgreSQL 式快照，只有 READ COMMITTED 與 REPEATABLE READ（先更新者勝）；SERIALIZABLE（SSI）不模擬，也不偵測 write skew。
  - 依實際執行偵測髒讀、不可重複讀、幻讀與遺失更新。
  - 練習答案由引擎算出（`src/lib/txn/check.ts`），題型有當機後的值、最後的值、發生哪些異常、最弱的足夠等級。錯的答案只得到提示，不會看到答案。
- 資料集 `sales`／`sales-b`：以遞迴 CTE 依固定算式產生（2,000 位顧客、200 項商品、30,000 筆訂單；隱藏版本 1,500／150／24,000），除了主鍵沒有任何索引，每次產生的資料都相同。
- 兩個活動都有：TypeScript 型別、活動 registry 的資料與文字替代說明、輸入驗證、重設、回饋、原生而且有標籤的表單元件（可以只用鍵盤操作）、手機版面、單元測試與瀏覽器測試。兩者都只在用到的課程頁載入。

## 內容與練習驗證

- SQL（真正的 SQLite）：
  - 每個範例的結果與頁面相同；預設查詢不出錯；
  - 參考解答與每個替代寫法在可見與隱藏資料（或隱藏檢查敘述）都通過，每個常見錯誤至少一組不通過；
  - 有計畫要求的練習，參考解答也必須符合要求，「結果對但計畫不符」的常見錯誤會被抓到；
  - DB13 的觸發器練習有隱藏的邊界檢查（例如剛好加薪 20%、多列 UPDATE 中有一列違規）。
- B+ 樹：每個範例都是合法的輸入，建出的樹通過不變式檢查。
- 交易：每個時間軸與排程都能執行；每道練習的答案由引擎算出，每個常見錯誤都被拒絕。DB15 撰寫者另外把內文描述的每個結果（讀到的值、等待、犧牲者、最後的值、切換模型與等級後的異常）都用模擬器核對過。
- 測驗：五堂 35 題由主線逐題對照資料校對；正式整合後再匯出一次，與校對版本逐字相同（DB12 在主線校對前已整合，以整合後的版本校對）。
- 主線修改的內容：DB12 的 CTE 改寫原本被計畫檢查誤判為不符，修正引擎後加入為替代寫法，並更新提示與計畫對照表。

## 已知限制

- SQL 練習場是學習用的隔離，不是安全產品等級的 sandbox；參考解答在頁面上。
- 計畫的範例結果（`id`、`notused` 欄）取自 SQLite 3.49.1；升級 sql.js 可能改變，測試會指出。
- `sales` 資料很規律（每位顧客總是買同一項商品等），練習是依此設計的。之後若修改產生資料的算式，要重新確認隱藏資料仍能區分答案。
- DB14 的 SQL 轉帳練習分不出「用 BEGIN…COMMIT」和「兩個自動提交的 UPDATE」，兩者最後的狀態相同。原子性改由時間軸練習檢查。
- 交易模擬是教學模型：不模擬 MVCC 的 SERIALIZABLE（SSI）與 write skew；WAL 模型不是 SQLite 的檔案格式。
- B+ 樹探索最多 40 個鍵、階數 3–6；練習場的執行時間會因電腦與次數而不同，教材只描述相對差異。
- P1-11、P1-32、P1-33、P1-34 仍未處理。
