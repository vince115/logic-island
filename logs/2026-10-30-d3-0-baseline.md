# 2026-10-30 D.3-0：正式版安全網與效能基準

> 授權範圍：批准 D.3-0～D.3-2，各自獨立 commit；正式 `/islands` 維持原版、不切換；不刪舊渲染器、不改預覽路由；不改 GLB 與保全庫；不做 Phase E／F；不 merge、不 push。D.3-0 只補測試與量測，不改任何使用者看得到的行為。

## 1. 正式 `/islands` 的安全網（E2E）

新增 4 項，桌機與手機各跑一次。斷言放在 `e2e/fallbacks.ts`，D.3-2 的 hex Explorer 會用同一組檢查：

| 測試 | 驗證內容 |
|---|---|
| 清單模式 | 按「清單」後畫布移除；三座島都能選、教材數正確（資料結構島 3、演算法島 2）、基礎程式島通往 `/learn`、BFS 附註連結在；切回「3D 群島」後 GLB 重新載入 |
| WebGL 無法建立 | init script 讓所有 WebGL context 請求回傳 null，渲染器掛載時丟錯；由 `SceneBoundary` 接住，沒有未捕捉錯誤；自動切到清單、提示出現、「3D 群島」停用，所有教材仍可到達 |
| WebGL context 中途遺失 | 以 `WEBGL_lose_context` 讓執行中的場景失去 context；結果同上 |
| BFS 入口 | BFS 不屬於任何島，頁面附註的「原有教材頁」連到 `/learn/bfs` 且可開啟 |

R3F 9 會把 WebGL 建立失敗轉成 render 錯誤，拋給最近的 React Error Boundary。正式版有 `SceneBoundary`；hex Explorer 目前沒有，同樣的失敗會讓整頁出錯，在 D.3-2 補上。

## 2. 資料一致性（單元測試）

`tests/world-data.test.ts` 把每份計算出的世界資料做 SHA-256 指紋（取前 16 碼），在 `42b32bc` 取值：

- A2 世界、道路、地形與 GLB 配置，以及 19 格原型，和 D.2b 起一路驗證的值相同；
- 37 格的世界、GLB 配置、自然配置、自然地形、海面網格、道路剖面與路面、森林與橋樑。

D.3 會在模組之間搬移程式；除非刻意改世界（commit 必須說明原因並更新指紋），這些值都不能變。

## 3. 可重現的效能量測方法

`playwright.perf.config.ts`＋`perf/world.perf.ts`，彙整用 `perf/summarize.mjs`；不屬於 `test:e2e`。

- **不靠 app 掛勾，任何路由都能量：**
  - 在頁面載入前包住 WebGL2 的 4 個 draw 函式與 `bindFramebuffer`，每幀記錄主畫面（預設 framebuffer）與離屏（陰影貼圖）的 draw call、三角形；
  - 用每個 Explorer 都有的側欄按鈕與「返回全景」讓鏡頭飛到基礎程式島再飛回來 3 次，量飛行中的 FPS 與幀間隔；
  - 記錄首幀與 GLB 就緒時間。
- **有實驗室探針的路由另外量：**
  - D.2c-2 的強制渲染（rAF FPS、讀像素同步的 frame time）；
  - **依島拆分的主畫面 draw call 與材質**：`canvas.__hexDraws()` 回報主畫面實際畫的物件，量測端依地塊歸屬分給各島。跨島的 instanced 物件（海、樹、岩石、道路、橋）算「共用」。
- **條件：**
  - production build，Chromium 156（Playwright 1.64.1）；
  - 桌機 1440×1000、DPR 1；手機為 iPhone 13 模擬（DPR 3，畫布上限 1.5）；
  - 鏡頭動畫開啟（不設 reduced motion）；
  - 每輪依序量完所有路由，輪流以抵銷機器負載變化。
- **環境變數：**
  - `PERF_BASE_URL`：已啟動的 production server；
  - `PERF_ROUNDS`：輪數；
  - `PERF_ROUTES`：要量的路由；
  - `PERF_GPU=metal`：改用 Mac GPU；
  - `PERF_CPU=4`：CPU 降速。

### 4.2 Apple M6 GPU（Metal）

- 兩條路由在四種情況的飛行與強制渲染都是 60 FPS，強制渲染的 frame time 為 0.7～1.0 ms。
- 首幀約 410～470 ms，GLB 就緒約 920～980 ms；37 格只比正式版慢約 35～55 ms。

### 4.3 手機模擬＋4× CPU 降速（3 輪）

| 指標 | 正式 `/islands` | 37 格實驗室 |
|---|---|---|
| 首幀／GLB 就緒（ms） | 924／1,058 | 1,574／2,268 |
| 鏡頭飛行 FPS | 60 | 56.2 |
| 強制渲染 FPS／frame time，全景 | — | 50.1／13.0 |
| 強制渲染 FPS／frame time，聚焦 | — | 46.1／14.9 |

降速確實生效（同一段計算由 15 ms 變成 58 ms），但兩條路由的數字與未降速時相近，表示瓶頸不在 JavaScript。

### 4.4 依島拆分（37 格實驗室，主畫面）

| 視角 | 基礎程式島 | 資料結構島 | 演算法島 | 共用（海、樹、岩石、道路、橋） | 合計 |
|---|---|---|---|---|---|
| 全景 draw call（材質） | 8（4） | 10（10） | 10（10） | 15（10） | 43 |
| 聚焦基礎程式島 draw call（材質） | 10（6） | 1（1） | — | 15（10） | 26 |

### 4.5 判讀

- **兩種場景的成本結構不同。** 正式版每幀 258 個 draw call（主畫面＋陰影），但三角形少、像素便宜；37 格只有 43 個，但三角形多、海面與地形填滿整個畫面。
  - 軟體算圖時，像素成本較重要，所以正式版較快：桌機飛行 60 對 38 FPS。
  - 真機 GPU 上 draw call 的 CPU 成本較重要，結果可能反過來。真正結論要等 D.3-4 的真機量測（P1-25）。
- **載入：** 軟體算圖下 37 格首幀晚約 0.6 秒、GLB 就緒晚約 0.9 秒；Metal 下只差約 0.05 秒，所以主要是算圖成本，不是 JavaScript。
- **單島預算（NEXT_STEPS §5.5：主畫面手機 ≤ 25、桌機 ≤ 35，材質 ≤ 10）：**
  - 以「該島自有＋共用」計算，聚焦基礎程式島時是 10＋15＝25，剛好達到手機上限；
  - 兩座暫代島各 10 個材質，也剛好達到上限；
  - 正式版沒有探針，無法拆分，但整體 146 個主畫面 draw call 已遠超過 3 × 25。

## 5. 建議門檻（待批准；D.3-1 起使用）

| 項目 | 建議門檻 | 依據 |
|---|---|---|
| 同一渲染器（D.3-1、D.3-2，以及日後 `/islands` 對實驗室） | draw call 與三角形**完全相同**；強制渲染與飛行 FPS 在同一輪量測中不低於基準的 90% | 這兩項是確定值；FPS 受機器負載影響，±10% 內視為相同 |
| 整個世界的主畫面 draw call | 全景 ≤ 45、聚焦 ≤ 30 | 現值 43／26，保留小幅餘裕 |
| 單島（自有＋共用） | 手機 ≤ 25、桌機 ≤ 35；材質以「自有」計 ≤ 10 | 現值 25；材質 6／10／10 |
| 閒置 | rAF 請求 0 | 現值 0 |
| 載入 | 首幀與 GLB 就緒不比基準慢超過 10% | 現值見 §4.1 |
| 對照正式 `/islands` | 只記錄、不設門檻；D.3-3 是否切換由產品與真機結果決定 | 兩者成本結構不同，見 §4.5 |
